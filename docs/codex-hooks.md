# Codex Hooks

This workspace includes a small Codex hooks layer under `.codex/`.

For the current Codex desktop workspace, `.codex/` should live at the workspace root:

    TwilightPrincessCo-op/.codex/

The Dusk repository itself is nested under:

    TwilightPrincessCo-op/dusk-coop/

If a future Codex session opens directly in `dusk-coop`, place or copy `.codex/` there instead.

## Purpose

The hooks are guardrails, not a replacement for judgment. They exist to preserve the project's working rules across new Codex sessions and context compaction:

- Load the current co-op plan context on session start.
- Remind Codex that the user owns Visual Studio/CMake builds unless explicitly requested.
- Block broad agent-issued staging commands such as `git add -A` and `git add .`.
- Block obviously destructive shell commands such as `git reset --hard`, forceful `git clean`, recursive `Remove-Item`, and `rm -rf`.
- Block co-op patches to original/decomp code when the patch lacks a `Co-op:` why-comment.
- Remind sessions and post-edit reviews to match local C++ style, including qualified class enum references in file-scope helpers and explicit fmt/MSVC casts for small integer, enum, `BOOL`, and bool-ish log arguments.
- Remind diagnostics-provider edits to keep `events.jsonl` bounded: semantic-change events, no empty/default spam, no frame-churn fields unless the profile specifically tests them, sensible cadence, and lean events versus richer `latest.json`.
- Remind enemy actor edits to classify player-singleton reads before patching: targeting, selected-target state, primary/global state, damage-owner, caught/grab-owner, or collision-owner. This is meant to prevent naive enemy-wide replacements and keep conversions routed through `enemy_targeting`.
- Remind enemy-targeting edits to use actor-local helpers, keep `EnemyTargetScope` as the behavior owner, keep callsite strings as diagnostic labels, use `EnemyTargetMode` for callsite policy, and avoid independent per-callsite retention machines.
- Remind target-dependent presentation and geometry edits that passive model callbacks, beam setup, and render-facing calculations consume retained target state read-only; they must not acquire, retarget, or advance retention before native awareness runs.
- Remind switch-gated enemy work to trace the authored switch producer before changing the waiting enemy. Generic `SwAreaC`/`SwAreaS` volumes must test each active player's native form/equipment condition and volume membership together, while preserving the volume's original latch/reset switch type.
- Remind world-trigger edits to classify activation eligibility, scripted subject, and presentation separately. Use `world_trigger` at the native transition; do not override canonical Link getters or replay trigger actors, and begin classified fullscreen presentation only after native demo acceptance.
- Remind enemy-targeting edits that `EnemyTargetResult::slot` is the durable identity and `EnemyTargetResult::localActor` is the local process pointer; do not reintroduce old `result.actor` usage in enemy patches.
- Remind damage-owner edits that nearest player and current enemy target do not answer "who hit me?"; route cut type/count, weapon-owner, hit direction, and hit-reaction ownership through `dusk::coop::damage_owner`.
- Remind enemy damage-counter edits that bespoke HP resets, special-hit counters, direct-hit bonuses, and object-threshold branches still need owner/collision classification; do not assume shared `cc_at_check()` damage covers them.
- Remind selected-target-state edits that target speed, facing, position, form, wolf-sense, wolf bark/threat, horse, swim, guard, and damage-state reads belong behind `dusk::coop::selected_target_state` once target identity is known.
- Remind enemy wake/state edits that converting the wake/read gate is not enough if the follow-up producer state still consumes P1. Trace wake -> state transition -> chase/attack/orbit producer before marking the enemy converted.
- Remind lock-on edits that "any player is locking this actor" and "which player/mode owns the lock" are different questions. Use slot-local `player_attention` to identify the locking player, and ask owner-local wolf-lock state before broadening vanilla P1 lock branches.
- Remind enemy steering edits that obstacle checks, detour angles, chase line probes, and home-range checks after target selection are selected-target state, while group "any active player near this teammate" checks belong to `player_query`.
- Remind enemy proximity edits to preserve the original distance dimension: XZ-only wake/drop/ground-range checks stay XZ-only, while full 3D distance is for height, pitch, aerial eligibility, projectile, or attachment geometry.
- Remind enemy/world-trigger edits that enemies blocked before action by authored room switches are not targeting failures; use switch diagnostics to distinguish upstream trigger producers from enemy-local authored wake gates. Patch known producers at the trigger; for enemy-local wake gates, preserve native switch flow from the active-player predicate instead of skipping the gate.
- Remind enemy-spawned weapon/child edits that launch and inherited attack intent should follow the parent/master combat target when the parent owns the attack, and parent hit-owner fields that seed child swarms or later pursuit must store the damage/item owner instead of P1. Nontrivial target snapshots should live in helpers when native switches use fallthrough or `goto`.
- Remind item-hit-spawned object edits that ownership may be consumed during the spawned actor's `create()` method. If a player-owned hookshot, boomerang, bomb, arrow, or similar item creates a new actor, pass the owner through the creation boundary instead of setting ownership afterward.
- Remind boomerang-carried object edits that `daPy_boomerangMove_c` and similar retained move helpers need the throwing slot from the hit collider or spawned object's owner. Do not let carried objects fall back to `daPy_py_c::getThrowBoomerangActor()` / `daAlink_getAlinkActorClass()` when P2+ owns the throw.
- Remind original actor/drop edits that the enemy death actor may only spawn effects while a separate pickup object owns the collection radius, draw-in matrix/effects, and player callback. Follow the producer into the pickup actor and retain the collecting slot with `retained_interaction_owner::Collect`; do not solve pickup bugs through enemy targeting.
- Remind defender/collision-owner edits that damage-owner, nearest player, selected target, and P1 globals do not answer "who did my attack touch?"; route enemy-attack guard/block/defender-state checks through `dusk::coop::defender_owner`.
- Remind caught/stun-owner edits that targeting and damage ownership do not answer "which player is retained by this effect?"; route scream/stun/grab/carry/hang release ownership through a retained owner API such as `dusk::coop::caught_stun_owner`, `dusk::coop::wolf_catch_owner`, or `dusk::coop::retained_interaction_owner`, and name local pointer caches explicitly, such as `localPlayerActor` or `affectedLocalActors`.
- Remind retained enemy demo edits to keep gameplay retention and presentation collapse separate: retain the caught slot in the matching retained-owner API, key split-actor interactions to the actor that consumes demo/camera state, and choose the retained slot's player camera. Use `event_presentation::Source::EnemyRetainedInteraction` only for a classified authored fullscreen surface; localized force-lock reactions such as the Tile Worm toss keep split-screen active and affect only the retained player's viewport.
- Remind authored P1 enemy-demo edits that `event_presentation::Source::EnemyAuthoredDemo` collapses presentation only: it does not retain a player, broaden the trigger, or transfer choreography ownership. Begin after native demo acceptance, end after native camera reset/start, and clear it during actor deletion.
- Remind mounted/ranged enemy edits that Rider-style enemies split into several owners: ordinary arrows and projectile launch math inherit the retained Combat target, rider-owned mounts inherit the rider target for steering, selected horse/boar/lock-on facts use `selected_target_state`, `horse_owner`, and `player_attention`, and coach/bridge/King Bulblin/setpiece targets stay authored until a dedicated encounter-owner policy exists.
- Remind item-awareness edits that boomerang, hookshot, bomb, bait, and similar immediate item/tool reactions belong behind `dusk::coop::item_awareness` or a narrow owner scan, not sticky combat targeting or P1 static helpers.
- Remind flying/vertical enemy edits that hover/orbit/dive positioning needs selected-target position/height facts, while retained wolf-bite ownership and item/tool awareness stay in their own APIs.
- Remind enemy awareness edits to apply native range, height, facing-cone, LOS, form, and status eligibility before nearest-player selection. Do not select nearest first and reject afterward, because an ineligible P1 can mask an eligible P2+.
- Remind enemy batch-conversion edits to update `docs/coop-enemy-audit.md` with every deferred or intentionally untouched API surface discovered while patching: camera/presentation ownership, master/child or spawned-enemy ownership, hookshot/item awareness, caught/grab/swallow/hang ownership, culling/render visibility, and remaining P1/global reads.
- Remind mixed-actor edits to classify the active native subtype/state before assigning ownership; one profile may combine ordinary combat, NPC interaction, retained collision/carry, and P1-authored first-encounter or miniboss branches that require different policies.
- Remind independent-player-control edits that raw P2 input is not enough; route ALINK lock-on, button status, item camera state, world prompts, and retained training state through the matching ownership family (`player_attention`, `player_button_status`, `player_camera_status`, `interaction_owner`, or `training_owner`) instead of borrowing P1 global attention/status.
- Remind UI/item edits to keep durable slot-local X/Y assignment in `player_item_selection`, meter prompt presentation in `hud_owner`, and transient viewport-local UI context in `ui_owner`. ## Limitations

Codex hooks are still guardrails. They do not intercept every possible tool path, and they do not replace code review. They also do not stop Codex app background Git integration outside the agent tool loop.

Keep hooks deterministic, fast, and narrow. Do not make hooks run builds or expensive scans.
